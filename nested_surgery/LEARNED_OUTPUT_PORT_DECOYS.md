# Does the frozen donor bridge help when Python contains misleading brackets?

The donor connection solved 256 of 256 original repair groups and switching off its donor erased 226. The equally sized bridge fed by the host solved 253, giving it little room to show a deficit. Here we keep every fitted bridge, projection and checkpoint frozen. Put bracket characters inside a string and a comment before the completion position. A parser ignores those copies when deciding which outer delimiter to close. A model that relied on nearby bracket patterns may lose accuracy. [Trained bridge and held-out evidence](learned_output_port_study/README.md)

Use 256 fresh triplets starting at ID 83000. For every decoy triplet, make a neutral companion with the same Python expressions, string and comment locations, line breaks and character lengths. Replace the bracket decoys with a fixed letter mapping. This controls formatting and leaves tokenizer segmentation free to change naturally. Confirm with execution that every prompt in each version has the same unique legal candidate as its source. Score the untouched 7B and 14B checkpoints, aligned, shuffled, and host-feature bridges, donor-off and cyclic exchange under both layouts. No fitting uses the new programs. [Runner](learned_output_port_decoys.py)

Require the neutral report to exceed the decoy report by at least 26 groups for the host-feature bridge, so the new challenge exposes at least ten points of headroom. On decoys apply the original matched criteria unchanged: at least 25 intact-donor-only opportunities, ten strict new donor-dependent solves on those opportunities, and five-point aligned gains over the three controls with positive paired lower bounds. An ordinary Python parser remains an exact baseline. This test measures transfer under one controlled lexical shift and leaves real code repair open.
